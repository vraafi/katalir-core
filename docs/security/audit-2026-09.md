## Perbaikan yang diterapkan

### L-1 → F-1 (High, sudah diperbaiki): guard anti-bocor kunci ikut bocor, tidak menolak

`tests/test_key_in_header_not_url.py::test_tidak_ada_kode_membangun_url_ber_kunci`
adalah guard yang memastikan tidak ada kode yang menaruh API key di query
string URL. Guard ini **tidak pernah berjalan** karena salah baca encoding:

`tests/test_self_healing.py` punya BOM UTF-8 yang sudah ter-commit. Test
membaca semua file `.py` dengan `encoding="utf-8", errors="replace"`, sehingga
BOM berubah jadi karakter `U+FEFF` di awal sumber, lalu `ast.parse()` melempar
`SyntaxError`. Hasilnya guard **crash**, bukan menolak — artinya file yang
melanggar aturan tidak pernah benar-benar diperiksa.

- **Perbaikan:** baca dengan `encoding="utf-8-sig"` (membuang BOM bila ada,
  tetap aman untuk file tanpa BOM).
- **Dampak:** setelah dibetulkan, guard langsung menemukan pelanggaran nyata
  yang sebelumnya tersembunyi (lihat F-2). Ini bukti bahwa guard tersebut
  memang load-bearing, bukan sekadar dekorasi.

### F-2 (Medium, sudah diperbaiki): API key di query string URL

Temuan yang terungkap oleh F-1 — ada di `scripts/gamedev/verify_gate.py:60`:

```python
url = ENDPOINT.format(model=MODEL) + "?key=" + api_key
```

Kunci di query string masuk ke access log, log proxy, dan bisa muncul di pesan
error, yaitu tempat yang tidak kita kendalikan. Repo ini sendiri punya
konvensi berlawanan: guard di atas mewajibkan header.

- **Perbaikan:** kirim lewat header `x-goog-api-key`, sesuai konvensi repo.

### Verifikasi bahwa perbaikan benar-benar bekerja

Guard diuji dengan **negative control** — menyuntikkan pelanggaran secara
sengaja lalu memastikan test GAGAL:

| Skenario | Hasil yang diharapkan | Hasil aktual |
|----------|----------------------|--------------|
| Kode bersih (perbaikan terpasang) | PASS | `67 passed` |
| Pelanggaran `?key=` disuntikkan | FAIL | `1 failed` — guard menangkap |
| File dipulihkan | PASS | header `x-goog-api-key` ada |

Tanpa langkah ini, "test hijau" tidak membuktikan apa pun.

## Temuan yang belum diperbaiki

### M-1 (Medium): CSP masih `Report-Only`, belum ditegakkan

Produksi mengirim `Content-Security-Policy-Report-Only`, bukan
`Content-Security-Policy`. Artinya kebijakan **belum memblokir** apa pun —
hanya mengumpulkan laporan pelanggaran.

- **Bukan bug, tapi keputusan yang belum selesai.** `public/_headers` dan
  `next.config.ts` sama-sama menjelaskan alasannya: CSP ketat bisa mematikan
  app (Next.js menyuntik inline script/style), jadi sengaja report-only dulu
  dengan rencana promosi ke enforce setelah 24 jam tanpa pelanggaran.
- **Perilaku yang sudah benar & dihormati:** `upgrade-insecure-requests`
  sengaja tidak dipasang karena ambigu pada mode report-only.
- **Risiko tersisa:** sampai dipromosikan, XSS yang berhasil dieksploitasi
  tidak akan diblokir CSP.
- **Rekomendasi:** pantau laporan pelanggaran 24 jam, lalu ganti
  `Content-Security-Policy-Report-Only` → `Content-Security-Policy`. Ini
  **perubahan deploy**, jadi butuh keputusan pemilik, bukan pekerjaan
  otomatis. Tidak saya ubah sekarang karena tidak ada bukti 24 jam laporan
  bersih.

## Catatan lain yang sudah diverifikasi sehat

- **Header produksi**: HSTS (dengan `includeSubDomains`), `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`
  (kamera/mikrofon/geolokasi dimatikan), plus NEL/Report-To aktif.
- **CSP `connect-src`** hanya mengizinkan origin sendiri, Railway, dan Supabase
  (+ `wss://` untuk realtime) — tidak ada wildcard.
- **`out/_next/static/*`** memakai cache immutable, sesuai dokumentasi
  Cloudflare untuk aset ber-hash.
- **CORS backend** memakai allowlist eksplisit (bukan `*`), konsisten dengan
  `allow_credentials=True`. Origin `https://evil.com` **tidak** mendapat
  header `Access-Control-Allow-Origin`.
- **Catatan pengujian:** `headers()` di `next.config.ts` **diabaikan** saat
  `output: "export"`. Sumber kebenaran header produksi adalah
  `public/_headers`. Ini sudah dikomentari di kedua berkas supaya tidak
  dikira tidak berfungsi.
- **Log `.err`/`.log`**: tidak ada yang ter-track di Git saat ini
  (`git ls-files` → 0). Scan history menemukan file log pernah ter-commit,
  tapi isinya hanya UUID, bukan credential.

## Batasan audit ini (jujur)

1. **Scanner pihak ketiga tidak tersedia** (`gitleaks`, `trufflehog`,
   `detect-secrets`, `pip-audit` gagal diinstal — jaringan/offline). Semua
   hasil di atas datang dari scanner lokal yang saya tulis sendiri, jadi
   cakupannya lebih sempit daripada gitleaks. Jalankan gitleaks di CI sebelum
   launch sebagai lapis kedua.
2. **Hanya ref lokal yang diperiksa.** Scan history memakai `git log --all`,
   yang mencakup ref lokal; branch/remote yang belum di-fetch tidak terlihat.
3. **Audit RLS baru diuji pada level "anonim tanpa apikey".** Supabase menolak
   di gateway dengan 401, jadi ini **belum membuktikan** bahwa RLS per-tabel
   benar-benar mengunci baris untuk pengguna yang *sudah login*. Membuktikan
   itu butuh kredensial user nyata dan Management API token — belum dilakukan.
4. **Probe otorisasi memakai `Expect: 401`.** Endpoint `POST /chat`,
   `POST /integrations`, `POST /mcp/install` membalas **422**, bukan 401 —
   artinya validasi body berjalan **sebelum** autentikasi. Ini bukan kebocoran
   data (tidak ada data yang dikembalikan), tapi menambah sedikit permukaan
   informasi bagi penyerang. Menilai ulang prioritas auth-vs-validasi adalah
   keputusan yang lebih tepat daripada saya ubah sendiri di produksi.
5. **Analisis dependensi belum tuntas.** `requirements.txt` mengunci FastAPI
   `0.115.6`; Starlette hanya transitif. CVE yang sempat disebut belum
   divalidasi terhadap pohon dependensi yang benar-benar ter-resolve, karena
   `pip-audit` tidak tersedia. Harus diverifikasi dengan tool yang bisa
   meng-audit environment sungguhan.
6. **Tidak ada credential yang dirotasi**, karena tidak ditemukan credential
   yang bocor.

## Triase temuan (ringkas)

- **History scan: 131 temuan mentah.** 124 di antaranya pola UUID (benih test,
  log, `dedup_canonical.json`) dan 7 temuan berbasis assignment. Ketujuhanya
  ditriase manual satu per satu (`triage_findings.py`): semuanya **false
  positive** — pembacaan env var (`os.getenv(...)`), akses properti DOM
  (`u.password`), dan string fixture lokal (`local-tests-...`). Tidak ada
  nilai credential di history.
- **Pola UUID adalah penyumbang utama noise.** Ini alasan kenapa laporan ini
  menulis "0 secret" dan bukan "131": angka mentahnya tidak berguna tanpa
  triase.

## Rekomendasi sebelum launch

1. Jalankan **gitleaks** (atau `pip-audit`) di CI — celah paling besar di
   audit ini adalah ketergantungan pada scanner buatan sendiri.
2. Putuskan **M-1**: promosi ke CSP enforce, atau biarkan report-only dengan
   alasan yang tercatat.
3. Validasi **RLS per-tabel dengan user yang sudah login** (butuh Management
   API token) — ini yang belum terbukti.
4. Selesaikan **audit dependensi** dengan tool yang bisa meng-audit
   environment ter-resolve.
