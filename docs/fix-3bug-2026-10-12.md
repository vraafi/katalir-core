## Bug S2 — Response 50 detik (target <30 s)

### 1. Model apa yang dipakai? — SUDAH BENAR

Benchmark `tests/user_test/latency_bench.py` (N=5): semua sampel memakai
`gemini-3.5-flash-lite`, `fallback_used: false`. Model bukan penyebabnya.

### 2. Fallback chain? — TIDAK jatuh ke model lambat

`fallback: false` di semua 5 sampel; tidak ada gateway fallback.

### 3. Hypothesis `thinking_level=low` — **DITOLAK DENGAN DATA**

A/B test identik (`tests/user_test/thinking_ab.py`, prompt + system sama):

| Konfigurasi | Mean latensi |
|---|---|
| A: default (tanpa thinking_config) | 12.666 ms |
| B: thinking_level=low | 12.487 ms |

Selisih **1,4%** — tidak signifikan. Perubahan ini **TIDAK dilakukan**;
hasil negatif didokumentasikan sebagai bukti.

### 4. Akar masalah sebenarnya: overhead prae-LLM tanpa batas

`meta.latency_ms` mulai dihitung di `_t0` yang berada **di dalam**
`_agentic_run_direct` — jadi yang selama ini dianggap "waktu LLM" tidak
mencakup 9 tahap serial di depannya:

```
auth → get_or_create_user → idempotensi → kuota → sesi → load_history
     → build_memory_context → add_message → pool/client → [LLM]
```

**Trace terisolasi** (`tests/user_test/overhead_trace.py`, lokal → endpoint
yang sama dengan produksi, `_overhead_trace.json`):

| Komponen | Hasil |
|---|---|
| RTT dasar Supabase (warm) | 62-115 ms |
| `gemini_key_pool.discover_keys` | 0,1 ms (bukan penyebab) |
| `generate_embedding` (HTTP Gemini) | **985-1.737 ms** (sekali **5.504 ms**) |
| `MemoryManager.recall` (embed+RPC) | **1.667-3.648 ms** |
| `list_preferences` | 93-1.209 ms |
| `build_memory_context` end-to-end | **1.262-3.346 ms**, worst case **tanpa batas** |

Worst case tanpa batas itu nyata: `generate_embedding` memakai
`httpx timeout=EMBED_TIMEOUT_S (8 s)` **per kunci** dengan rotasi hingga
13 kunci → kala embedding lambat, satu giliran chat bisa menunggu puluhan
detik hanya untuk konteks memori (data sekunder!). Ini menjelaskan varians
overhead 8 s ↔ 23,7 s pada benchmark.

### Perbaikan (3 lapis, semua defensif-total)

1. **api_server.py — time-box keras** (`_build_memory_context_timeboxed`):
   `build_memory_context` dijalankan di worker thread dengan deadline
   `MEMCTX_DEADLINE_S` (default **2,5 s**, env-adjustable). Lewat anggaran →
   chat berjalan **tanpa** konteks memori (degradasi anggun — pola baku
   context-building LangChain/LlamaIndex; memori = nice-to-have, bukan
   prasyarat jawaban). Worker yang tertinggal selesai di belakang dan
   hasilnya dibuang; `max_workers=4` supaya burst tidak mengantri.
   Unit test: deadline 1 ms → `""` tanpa error; deadline normal → string.
2. **memory_manager.py — paralel + cache**: `recall` (HTTP embedding + RPC
   pgvector) dan `list_preferences` (RPC) saling independen → dijalankan
   **paralel** (ThreadPoolExecutor). Preferensi di-cache per user TTL 5
   menit (`MEMORY_PREFS_CACHE_TTL_S`); `set_preference` membuang cache.
   Pengukuran ulang: `build_memory_context` kini mengikuti latensi recall
   saja (~1,7 s typical), preferensi 75-100 ms (cache hit).
3. **Instrumentasi `[perf]`**: satu baris per request di log produksi:
   `[perf] /chat total=…ms llm=…ms memory=…ms model=…` — overhead tak
   terlihat selama ini kini terukur terus-menerus.

## Bug S5 — Form credential tidak render (PALING PENTING)

### Diagnosa (sesuai 4 langkah brief)

1. **`/chat` return `credential_form`?** TIDAK — `_s5_diag.json` (raw):
   `status:"success"`, kunci hanya `meta/reply/session_id/status`,
   `latency_ms: 2232`, tanpa `requires_credential`/`fields`/`resume_token`.
2. **`useChat.ts` render `<CredentialForm>`?** YA untuk jalur
   `requiresCredential` (thread.tsx:270-276 merender bila
   `fields`/`resumeToken` ada) — tetapi jalur itu tidak pernah terjadi
   karena backend tidak pernah mengirimnya.
3. **AI bilang "form di bawah" tapi backend tidak kirim?** TEPAT. Model
   menjawab teks yang meminta info (pertanyaan klarifikasi), TANPA memanggil
   tool → `CredentialMissingError` tidak pernah naik → kartu tidak pernah
   dibangun. Ini bukan bug frontend; ini **gap kontrak**.
4. **Fix dua sisi:**
   - **Backend** (`_maybe_proactive_credential`): pada jalur sukses, bila
     (a) pesan user menyebut provider ber-form inline (telegram/gmail_imap/
     supabase, word-boundary), (b) reply sedang meminta informasi
     (`?`, "butuh", "silakan", …), (c) credential BELUM ada, (d) provider
     punya form inline → susun kartu `credential_prompt` dan kirim
     **bersama** `status:"success"` + teks reply (reply TIDAK dibuang),
     lalu persist kartu (tahan refresh/navigasi).
   - **Frontend** (`useChat.ts` branch `credentialPrompt`): teks asisten
     dipertahankan, kartu form ditambahkan **setelahnya** (jalur lama
     menggantikan bubble → penjelasan model hilang). Bila reply kosong,
     kartu menggantikan bubble (perilaku lama).

### Bug ekstra yang ditemukan saat review render pipeline

Kartu proaktif mula-mula TIDAK diberi `_localId`. Review `ChatApp.tsx`
menunjukkan overlay render hanya meneruskan entri **ber-`_localId`**
(line 429-434, dedup per `_localId`) — persis bug class yang pernah
menimpa kartu approval ("pesannya ada di cache, tidak pernah tampil").
Kartu kini diberi `_localId` **unik** (berbeda dari bubble asisten — bila
sama, dedup overlay membuang entri kedua). Verifikasi `ThreadItem`
mapping (`cred-…`) menerima kartu via `m.id ?? m._localId`.

## Bug S9 — Prompt panjang

### 1. Batas karakter sebelumnya? — TIDAK ADA

`ChatRequest.prompt: str` tanpa validator; textarea tanpa `maxLength`.
Paste 10 MB pun lolos sampai ke LLM.

### 2-3. Implementasi + hasil unit (sebelum deploy)

- **Backend**: `CHAT_MAX_CHARS = 8000` (acuan industri: batas pesan ChatGPT
  free tier; riset 12 Okt). Pydantic `field_validator` menolak dengan 422
  + pesan actionable:
  `Pesan terlalu panjang: 12,000 karakter. Batas 8,000 karakter per pesan.
  Kurangi sekitar 4,000 karakter, atau pecah menjadi beberapa pesan.`
  Unit: 40 OK · 12.000 DITOLAK · 8.000 OK · 8.001 DITOLAK.
- **Frontend**: `maxLength={8000}` (ChatApp → ChatComposer) menempel ke
  `<textarea>` (browser clamp ketikan/paste di sumbernya); counter
  `[data-testid="composer-counter"]` muncul saat ≥80% terisi
  (`aria-live="polite"`), merah saat ≤5% sisa — umpan balik SEBELUM user
  kena error.

### Hasil produksi (frontend terdeploy, terverifikasi Playwright)
